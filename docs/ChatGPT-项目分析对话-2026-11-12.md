### 4.0 先说对项目的初步理解

> 蓝余汐为人格主体、DSH 为运行环境、QQ 为社交入口、独立文件目录为长期生活空间。

### 4.1 第一轮架构评审：已经发现的几个问题

> 你的产品设计比目前的工程实现更成熟。

> 产品需求已经考虑到了很多容易遗漏的细节，例如：

- 两本日记的隐私隔离。
- 群聊与私聊不同的行为规则。
- 社交暂停、静音等紧急刹车。
- 本地素材与代码仓库分离。
- 语音引擎失败时自动降级。
- 不同社交平台共享同一个人格主体。

> 但我已经看到一些需要重点核查的地方。

#### 问题 1 · 会话切分机制可能存在设计冲突（index.js）

> 这两套规则必须明确谁是最终依据。我更建议：

- 会话切分只由上下文使用量决定。
- 日期只负责标题、归档和日记。
- 每次切分必须保留上一会话的可检索索引。
- 新会话不能只知道上一个 ID，还要知道旧会话的摘要、关键人物、重要约束。

> 否则可能出现一种情况：新会话知道以前存在某个会话，却不知道该检索什么，最后仍然丢失重要记忆。

#### 问题 2 · 发言配额需要重新核对（index.js）

> 涉及 maxOutboundPerDay / groupOutboundPerDay / Quota / count。

> 这与需求中私聊、群聊分开计数的规则存在潜在冲突。建议改成独立计数：

| 类型 | 独立计数 |
|---|---|
| 主人私聊 | 私聊每日上限 |
| 群聊 | 群聊每日上限 |
| 其他平台 | 各平台独立配额 |

> 并且必须在真正发送成功后计数，而不是仅仅在准备发送时计数。

#### 问题 3 · 消息去重的时机需要调整（handleEvent()）

> remember(event.message_id) 的位置有问题：这意味着重复推送的 QQ 事件，有机会先进入群上下文，再被判定为重复消息。建议把处理顺序调整为：

    收到事件
      ↓ 验证事件类型
      ↓ 检查 message_id 是否重复
      ↓ 检查发送者和群权限
      ↓ 检查是否 @ 本人
      ↓ 解析文本、图片等消息
      ↓ 写入群上下文
      ↓ 交给 AI
      ↓ 检查出站权限和配额
      ↓ 发送消息

> 这个问题不一定每次都造成重复回复，但会污染上下文。

#### 问题 4 · 最严重的问题：不同聊天之间可能串消息

> 这是我目前最希望你优先处理的地方。

> 你的设计是「主人私聊 + QQ 群聊 → 蓝余汐同一个 Agent」。我理解你想让她无论在哪里都保持同一个人格、同一份记忆。但是目前代码里有两个全局变量：lastChat、sessionState.current，qq_send 依赖 lastChat。

> 这里存在一个实际的并发风险：

    1. 主人私聊：今天吃饭了吗？
    2. QQ 群：有人 @ 蓝余汐
    3. lastChat 被更新为群聊
    4. AI 处理第一条私聊消息
    5. AI 调用 qq_send
    6. 原本应该发给主人，结果可能发到群里

> 这不仅是普通 Bug，还可能导致主人私聊内容泄露。

> 另外，共用同一个 Agent 会让群聊上下文和主人私聊上下文混在一起。即使系统提示要求她不泄露，也不能把模型的自觉当作安全边界。

> 我的建议：保留一个人格主体，但把对话上下文隔离。

| 层 | 内容 |
|---|---|
| 共享：蓝余汐人格主体 | 人格卡 · 纠正清单 · 公共偏好 · 工具能力 |
| 主人私聊 Agent | 私密上下文：私人记忆、私人日记、主人对话 |
| QQ 群 Agent | 群聊上下文：群聊记录、群成员、群聊话题 |
| 受权限控制的长期记忆检索 | 只允许读取当前场景有权限访问的记忆 |

> 这样她仍然是同一个蓝余汐，但不会因为在群里聊天，就把主人私聊的内容带出去。

#### 问题 5 · HTTP 面板接口存在安全隐患

> 这是我认为应该列为最高优先级的问题之一。index.js 的 /lanyuxi 系列接口：

| 接口 | 当前行为 | 风险 |
|---|---|---|
| /diary | 可以读取 private 日记 | 高 |
| /webui | 返回 NapCat WebUI Token | 高 |
| /persona | 读取、修改人格文件 | 中高 |
| /brakes | 修改静音、社交暂停状态 | 中高 |
| /start、/stop | 启动、关闭 NapCat | 中高 |
| /bili | 接收并保存 B 站 Cookie | 高 |
| /open | 启动本地 Explorer | 中高 |

> 目前我没有在这些路由处理代码中看到统一的身份验证、权限验证和 CSRF 防护。

> 这里需要注意：即使 DSH Web 默认只监听本机，也不代表没有风险。恶意网页可能尝试向本机服务发起跨站请求。

> 我的建议：

- 所有写操作必须进行身份认证。
- 检查请求来源 Origin 和 Host，不能只依赖浏览器同源策略。
- 写操作统一使用 POST，并增加 CSRF Token。
- NapCat Token 绝不能通过普通面板接口返回明文。
- 所有敏感接口增加权限分级和审计日志。
- 尤其是日记接口：私人日记的访问权限应该在服务端强制执行，而不是仅仅隐藏前端按钮。

#### 问题 6 · 会话用量计算不够准确

> 你目前的切分机制是：

    function currentLimit() {
      const window = config.contextWindowTokens || 1048576
      const cpt = config.charsPerToken || 1
      return Math.max(1000, Math.floor(window * (settings.rolloverPercent / 100) * cpt))
    }

> 然后在收到消息时：cur.chars += textLength

> 这里有一个问题：**你统计的是收到的文本字符数，而不是实际使用的上下文 Token。** 没有完整计入：

- AI 自己输出的内容。
- System Prompt。
- 工具调用和工具返回结果。
- 跨段注入的记忆。
- 图片、音频等多模态内容。

> 所以 50% 这个阈值，并不一定代表真实上下文已经使用 50%。
> 建议优先读取 DSH 会话的实际 Token 使用量。如果暂时无法取得，就采用输入、输出、工具结果的累计估算，并把系统提示等固定开销纳入预算。
> 还有一点：不要直接假定所有模型都是 1048576 Token 窗口，应该根据当前模型能力动态设置上限。

#### 问题 7 · 发送队列存在绕过限制的可能

> 这个问题比表面上的配额计算更值得注意。我检查了 drainOutbox()，发现它有几个问题：

1. 消息排队后，如果主人开启静音或暂停社交，队列仍可能继续发送。
2. 队列补发成功后，只执行 quota.mark()，没有执行 groupQuotaMark()。
3. 循环中使用异步 request()，没有等待上一条发送完成，可能同时发出多条消息。
4. 队列中的消息没有在真正发送前重新验证全部权限。

> 举个例子：主人让她在群里发一句话，她因为冷却而排队。随后主人点击了「暂停社交」，但两秒后队列仍可能把之前的消息发出去。

> 建议把发送流程统一成一个 MessageDispatcher：

    所有发送请求
      ↓ 进入统一队列
      ↓ 重新检查目标与权限
      ↓ 检查静音 / 社交暂停
      ↓ 检查禁说清单
      ↓ 检查每日配额
      ↓ 检查冷却
      ↓ 发送 QQ
      ↓ 确认成功
      ↓ 持久化配额与发送记录

> 排队不代表获得了永久发送许可。

#### 问题 8 · 文件路径安全检查不够严谨

> 目前图片发送和表情收藏使用了类似 imgPath.toLowerCase().startsWith(home) 来判断图片是否属于她的家目录。这个判断不够安全。例如：

    E:\dsh-foundry\lanyuxi-home\stickers\a.png
    E:\dsh-foundry\lanyuxi-home-evil\secret.png      ← 第二个路径也能通过前缀检查

> 应改用 path.resolve() / path.relative() 判断。

> 另外，收到 QQ 图片时（fetch → Buffer.from(await res.arrayBuffer())）目前没有看到下载超时、文件大小限制和严格的文件类型校验。建议增加：

- 仅允许可信图片 CDN 域名。
- 禁止访问 localhost、内网 IP 和非 HTTPS 地址。
- 限制单张图片大小，例如 10 MB。
- 下载超时。
- 根据文件魔数验证真实图片格式。
- 下载失败不能阻塞整个消息处理。

> 因为群友发图片属于外部输入，这个入口应该按不可信数据处理。

#### 问题 9 · 备份清理可能失效（backupSessions()）

> 它采用递归复制目录，但是清理旧备份时：

    for (const n of readdirSync(join(backupRoot(), old))) {
      try { unlinkSync(join(backupRoot(), old, n)) } catch {}
    }
    rmdirSync(join(backupRoot(), old))

> 由于异常被忽略，你可能以为只保留了 14 份备份，实际却积累了更多。建议直接采用 Node.js 的递归删除：

    import { rmSync } from "node:fs"
    rmSync(oldBackupPath, { recursive: true, force: true })

> 同时，备份最好采用临时目录复制完成后再原子重命名，避免复制中断时留下不完整备份。

### 5.1 重新定义整体架构

| 系统 | 内容 |

| 感知系统 | QQ / B站 / 微信；文字 / 图片 / 音频 / 视频 |

### 5.2 最重要的设计：不要把「学习」等同于训练大模型

> 这是整个项目最容易走偏的地方。我建议把蓝余汐的成长分成五个层次。

- **第一层：经历积累（Experience）**——她通过 QQ、微信、B站等媒介接触到的信息，形成原始经历。例如：今天主人心情不好、群里讨论了一个新技术、看了一段游戏攻略。
- **第二层：知识与记忆（Memory）**——从经历中提取人物、事件、知识、偏好、关系和重要信息。不只是保存聊天记录，而是理解聊天记录代表什么。
- **第三层：反思与理解（Reflection）**——她需要定期回顾自己的经历：我今天学到了什么？我对某件事的理解是否正确？我是不是误解了某个人？我之前的判断有没有被新信息推翻？
- **第四层：能力成长（Capability）**——学会使用新工具、掌握新技能、形成解决问题的方法。比如从观看大量 Unity 教程，到能够独立完成一个简单的 Unity 项目。
- **第五层：人格演化（Personality Evolution）**——根据长期经历形成稳定的偏好、行为习惯、表达风格和价值判断。不是今天开心就修改性格，明天难过就换一个人格，而是经过长期经验逐渐调整。

> 这里有一个技术上的关键：短期记忆、长期记忆、知识库、技能库、人格参数和模型权重，应该是不同的东西。
> 我不建议每次聊天后都拿数据去微调模型。更合理的顺序是：

1. 先通过记忆检索让她记住经历。
2. 再通过反思让她形成稳定认知。
3. 再通过技能系统让她真正掌握能力。
4. 积累足够高质量、经过筛选的数据后，再考虑 LoRA 或其他微调方式。

> 微调主要改善模型的表达、行为模式和特定任务能力；它不是可靠的个人经历数据库，也不能保证模型真正记住某个人。

### 5.3 QQ / B站 / 微信应该如何提供数据

      ↓
    认知处理流水线

      · 形成成长素材：经验、技能、人格观察
      ↓
    个人记忆库 / 知识库 / 技能库 / 人格成长档案

> 这套设计有一个很重要的好处：以后哪怕你把 QQ 换成其他聊天平台，也只需要开发一个新的数据适配器，蓝余汐的认知和记忆系统不需要改变。

| 数据来源 | 主要学习内容 |
|---|---|
| 主人私聊 | 主人的习惯、关系、共同经历、交流方式 |

| 第一层：核心身份 | 高度稳定 | 身份认知、核心价值观、重要行为底线、自我身份连续性。不能因为普通聊天、外部信息或一次模型判断就被修改 |
| 第二层：性格特征 | 缓慢演化 | 好奇心、幽默感、主动性、表达习惯、社交倾向、兴趣偏好。根据长期经历和多次验证逐渐调整 |
| 第三层：当前状态 | 动态变化 | 当前心情模拟、注意力、疲劳状态、近期兴趣、当前目标。可随互动和任务变化，不需要永久写入人格 |

> 举个例子：蓝余汐最开始比较安静，不太主动聊天。经过长期与主人交流、参与 QQ 群讨论、学习新知识，她逐渐发现自己对某些话题特别感兴趣，也更愿意主动分享。那么系统可以这样变化：

    原始人格：社交主动性 0.35，好奇心 0.60，幽默倾向 0.50
    长期经历：多次主动参与技术讨论；多次主动分享有趣内容；主动探索新知识获得积极反馈
    人格观察：对技术话题主动性持续提高
    候选调整：社交主动性 0.35 → 0.40
    验证：持续观察一段时间，检查是否只是短期状态
    最终：经历充分验证后，才正式…（代码块折叠，原文在此截断）

> 这里的数值只是工程设计示例，不是说人类性格能够被准确压缩成几个数字。
> 我还建议保留人格变更历史，记录：原来是什么、为什么发生变化、哪些经历支持这个变化、是否经过验证、什么时候生效、是否可以回滚。

> 这样你可以看到蓝余汐的成长轨迹，而不是每次修改人格文件后都不知道她为什么变了。

### 6.3 统一记忆系统：所有平台进入同一个认知世界

> 这是整个项目最核心的基础设施。但是，我不建议把所有数据直接混成一个数据库表，或者不区分来源地全部放进向量数据库。正确的设计是：
> **统一记忆索引 + 分类存储 + 来源追踪 + 权限控制**

**3.1 记忆分为六种**

| 记忆类型 | 具体内容 | 示例 |
|---|---|---|
| 情景记忆 | 发生过什么 | 今天和主人聊了游戏开发 |
| 人物记忆 | 认识谁、有什么特点 | 某位朋友喜欢讨论 AI |
| 关系记忆 | 人与人之间的关系 | 主人和某朋友经常一起玩游戏 |
| 语义记忆 | 学到的知识和事实 | Java 异步任务的原理 |
| 程序性记忆 | 学会如何完成事情 | 如何创建 ComfyUI 工作流 |
| 自我记忆 | 自己的经历与变化 | 我曾经在某次任务中犯过什么错误 |

> 这六类记忆不是孤立的。例如：蓝余汐在 B 站看到一个 Unity 教程，随后主人在 QQ 里询问如何实现角色移动，她利用之前学到的知识回答，最后通过实际运行验证成功。这个过程会产生：情景记忆（观看了某教程）、语义记忆（理解角色移动原理）、程序性记忆（掌握具体实现方法）、自我记忆（曾经成功解决类似问题）。
> 这才是真正的跨平台学习。

**3.2 记忆必须有来源和权限**

> 建议每一条记忆都包含以下字段：

    {
      "memory_id": "mem_000001",
      "type": "episodic",
      "content": "今天学习了Unity角色移动",
      "source": { "platform": "bilibili", "source_id": "video_123" },
      "subject": "lanyux…（代码块折叠，原文在此截断）

> visibility 取值：private / shared / public / restricted。
> 注意：统一认知并不意味着所有内容都可以跨场景读取。例如，主人在 QQ 私聊中透露的私人信息，即使进入统一记忆索引，群聊 Agent 也不能读取。**系统应该在检索阶段就执行权限过滤，而不是让模型读取之后再要求它保密。**

**3.3 记忆不能只有增加，还要支持更新和遗忘**

> 这点非常重要。如果蓝余汐不断积累信息，却不会修正旧信息，几年后就会出现大量冲突记忆。例如：

    2026年：主人喜欢游戏A。
    2027年：主人已经不再玩游戏A，开始喜欢游戏B。

> 不应该简单地保存两条互相冲突的事实。应该建立记忆生命周期：

    新信息 → 判断是否已有相关记忆 → 比较时间、来源、可信度
      → 新增 / 更新 / 标记过期 / 保留争议 → 建立关联 → 进入记忆索引

> 同时保留历史版本，支持用户要求纠错和删除。

### 6.4 自主学习系统

> 这是我认为蓝余汐未来最有价值的功能。你希望她不是等主人教她，而是可以通过外部世界主动学习。

| 学习类型 | 含义 |
|---|---|
| 被动学习 | 观看视频、阅读聊天、接触新知识 |
| 主动学习 | 自己搜索资料、阅读文档、探索未知 |
| 实践学习 | 编写代码、调用工具、完成实际任务 |
| 反思学习 | 分析错误、总结经验、更新认知 |

**4.2 学习过程的闭环**

1. **发现学习机会** —— 遇到未知知识、发现兴趣、收到任务
2. **制定学习目标** —— 要学什么？为什么学？学到什么程度？
3. **资料收集与理解** —— 搜索、阅读、视频理解、知识提取
4. **知识整理与实践** —— 建立知识条目、编写实验、执行任务
5. **能力评估** —— 是否理解？能否独立完成？能否迁移？
6. **更新知识库与技能库** —— 保留证据、经验、错误和能力等级

**4.3 学习目标管理器**

    学习目标：掌握 Unity 2D 角色动画系统
    当前进度：

      理解 Animation Clip：已完成
      学习状态机：进行中
      完成角色 Idle / Walk：未完成
      完成攻击动画：未完成
      独立制作一个完整角色控制器：未完成
    能力评估：理论理解 60% / 实践能力 30% / 独立解决问题 2…（原文截断）

> 这会让她拥有持续推进的学习任务，而不是每次聊天都从零开始。
> 但是，高自主性不意味着无限制行动。我建议建立行动等级：

| 等级 | 行为 | 权限 |
|---|---|---|
| L0 | 读取已授权信息 | 自动 |
| L1 | 总结、整理、建立记忆 | 自动 |
| L2 | 搜索、学习、测试代码 | 受资源与环境限制自动执行 |
| L3 | 发布动态、主动联系他人 | 按平台和对象授权 |
| L4 | 付款、删除重要数据、公开私人内容 | 必须主人明确批准 |

> 她可以自主制定目标、安排学习计划，但不能自行扩大数据采集范围或突破权限。

### 6.5 认知与反思系统：世界模型

> 不是让蓝余汐真的建立一个完整的物理世界模拟器，而是让她逐步维护一份关于自己所处世界的结构化认知。例如：

    人物
      ├── 主人：兴趣 游戏开发、AI；技术 Java、ComfyUI；关系 重要的人
      ├── 朋友A：兴趣 游戏；关系 群友
    知识
      ├── AI：LLM / Agent / MCP / Skills
    经历…（原文截断）

> 世界模型可以通过知识图谱、关系数据库和记忆检索共同实现，不需要一开始就引入复杂的图数据库。

**5.1 每天进行一次自主反思**（不是简单生成一篇日记）

| 反思方向 | 需要思考的问题 |
|---|---|
| 经历回顾 | 今天发生了什么重要事情？ |
| 知识学习 | 今天接触到了哪些新知识？ |
| 认知检查 | 有没有错误理解或未经验证的结论？ |
| 人物关系 | 有没有新的关系变化？ |
| 自我观察 | 今天的行为有没有体现出新的倾向？ |
| 目标进度 | 正在学习的事情有什么进展？ |
| 下一步计划 | 明天有哪些值得继续探索的事情？ |

> 反思结果进入成长档案，但**不允许直接修改核心人格**。

**5.2 认知冲突处理**

> 例如：以前认为 A 技术最好，今天学习了 B 技术，发现 B 在特定场景更合适。不能直接把旧知识删除，应该记录适用条件，重新调整自己的判断。建议知识记录具备：

    观点：某技术方案适合小型项目。
    支持证据：文档、实验、实际使用经验。
    反对证据：大规模项目中存在性能瓶颈。
    当前结论：小型项目适合，大型项目需要进一步评估。
    可信程度：中高。
    下次验证：实际项目压测。

> 这比简单地让模型把知识写入 Markdown 文件可靠得多。

### 6.6 高自主性系统：任务调度和行动循环

> 她应该拥有自己的运行循环。我建议采用 **Event-driven + Scheduled Reflection + Goal-driven Agent** 三种机制结合。

| 机制 | 作用 | 示例 |
|---|---|---|
| 事件驱动 | 外部发生事情时响应 | QQ 有人发消息 |
| 定时驱动 | 定期整理和反思 | 每晚整理当天经历 |
| 目标驱动 | 为长期目标主动行动 | 自主学习 Unity |

    外部事件 → Event Collector → Cognitive Engine
      ├→ 需要回复 → 对话规划 → 权限检查 → 执行行动
      └→ 发现学习机会 → 创建学习目标 → 学习任务队列 → 学习与实践
                                                    ↘（汇总）…（原文截断）

> 这里有个工程设计重点：**不要让一个 Agent 同时负责聊天、学习、记忆整理和人格修改。** 建议采用多个有明确职责的 Agent 或工作流：

- Conversation Agent：日常对话。
- Research Agent：资料搜索和学习。
- Memory Agent：记忆整理。
- Reflection Agent：自我反思。
- Planner Agent：长期目标规划。
- Action Agent：执行工具任务。
- Supervisor：审核权限、预算和运行状态。

> 这些不一定要部署七个不同的大模型。完全可以先用同一个模型，通过不同的任务提示、工具权限和独立上下文来实现。这样成本更低，也更容易维护。

**6.1 自主行动必须有资源管理**

> 建议增加一个统一的资源调度器：每日 Token 预算、搜索次数限制、视频学习时长、任务最大执行时间、最大并发任务数、失败重试次数、学习优先级、任务暂停与恢复。否则高度自主的 Agent 很容易陷入：

    发现问题 → 搜索 → 发现更多问题 → 继续搜索
      → 搜索结果不满意 → 换关键词 → 再搜索 → Token 消耗完毕

> 自主性越高，越需要严格的调度和停止条件。

### 6.7 数据库设计：从一开始就给未来留好位置

> 结合你现在的 Java / Node.js 开发经验，我建议采用：

- **SQLite**：本地运行的第一阶段数据持久化。
- **PostgreSQL**：未来多平台、多任务并发时的升级选择。
- **pgvector 或独立向量索引**：语义检索。
- **文件系统**：图片、音频、视频、原始资料。
- **Redis**：可选，用于短期任务队列和状态缓存。

> 不要一开始就把所有内容都放进向量数据库。关系型数据库负责事实和权限，向量索引负责语义召回，文件系统负责原始素材。

3. 所有学习结果必须有验证记录，不能仅凭模型自评就认定掌握。

### 6.9 开发路线：不要一口气做出完整的智能人（四个大版本）

| 版本 | 目标 | 内容 | 验收标准 |
|---|---|---|---|
| V1.0 · 拥有记忆（第一目标） | 从机器人到连续存在的角色 | 统一数据接入、统一记忆系统、私聊/群聊/B站数据分类、人物和关系管理、跨会话记忆检索、日记与成长档案 | 重启、更换会话、更换平台后，仍能准确调用以前积累的记忆 |

| V3.0 · 拥有成长能力 | 从固定人格到持续成长 | 每日反思、认知冲突处理、人格特征演化、长期目标、自主学习计划、成长时间线 | 能够解释自己的认知变化，并提供支持这些变化的经历和证据 |

### 6.10 现在先做一个最小可运行的成长闭环

> 不要先急着开发所有模块。先让蓝余汐完成一次完整的成长过程（V1 核心验收场景）：

1. QQ 群有人讨论 Unity 角色动画。
2. 蓝余汐识别出这是一个值得学习的新知识。
3. 将群聊事件保存到经历库。
4. 主动搜索 Unity 官方文档。
5. 提取 Animator 和 Animation Clip 的知识。
6. 创建一个 Unity 学习目标。
7. 编写并运行一个简单测试。
8. 验证成功后，将结果写入技能库。
9. 晚上进行反思，记录当天的学习成果。
10. 第二天主人询问 Unity 动画时，能够调用之前的学习成果。

> 完成后，你就拥有了一个最基础的「感知—记忆—学习—实践—反思—再利用」闭环。
> 这里我特别建议增加一个测试：关闭蓝余汐，隔一天重新启动，清空当前会话，然后重新问她之前学到的内容。如果她还能找到正确的学习经历、知识来源和实践结果，才说明这套长期记忆真正发挥作用了。

### 6.11 必须提前考虑的技术问题：模型无关的人格层

> 你未来很可能会遇到一个问题：如果以后 GPT 换成 DeepSeek，或者换成其他模型，蓝余汐会不会变成另一个人？我建议从现在开始建立模型无关的人格层。

| 内容 | 是否依赖模型 |
|---|---|
| 人格核心 | 不依赖 |
| 记忆数据库 | 不依赖 |
| 人物关系 | 不依赖 |
| 知识库 | 不依赖 |
| 技能库 | 不依赖 |
| 学习目标 | 不依赖 |
| 语言表达能力 | 依赖模型 |
| 推理能力 | 依赖模型 |
| 视觉理解能力 | 依赖模型 |
| 语音表现 | 依赖语音模型 |

> 未来更换模型时，只需要更换认知引擎，重新适配工具调用和模型能力，不应该重新培养她的全部记忆。
> 另外，建议先用模型提示词、记忆和技能系统实现成长，等积累足够数据后再考虑微调。**不要让微调成为整个项目的基础设施依赖。**

### 6.12 学习边界：感知权、认知权、行动权

> 你选择了高度自主，这就涉及她究竟可以主动学习什么。我认为有三种能力需要区分：**感知权、认知权、行动权**。
> 三者不能自动等同。例如，允许她阅读某个 QQ 群，不代表允许她将群内私人聊天永久保存，更不代表允许她把群聊内容公开发布。
> 我建议默认采取最小权限、逐步授权的策略。

**第二轮末尾的三个待确认问题：**

1. 她可以主动接触哪些学习资料？
2. 她应该怎样产生自己的学习目标？
3. 未来是否希望蓝余汐拥有专属模型？

> 我的最终想法是：先让蓝余汐拥有可靠的记忆，再让她拥有真正的学习能力，最后才是人格演化和高度自主。

### 一、为什么我不推荐直接 Python + MySQL？

> 你可能会考虑 Python，是因为现在 AI 领域的生态基本以 Python 为主。确实如此：

| 能力 | Python 侧 | Node.js 侧 |
|---|---|---|
| 文档解析 | 非常优秀 | 较好 |
| 视频、音频处理 | 非常优秀 | 较好 |
| PyTorch / Transformers | 原生生态 | 间接调用 |
| QQ / DSH 现有接入 | 需要重写或桥接 | 原生延续 |
| 现有项目迁移成本 | 较高 | 较低 |

> （原表表头在上一屏，本稿按列内容还原为「Python / Node.js」两列。）

> 你当前的 DSH 插件本身就是 Node.js 生态。如果直接把核心代码全部改为 Python，就意味着：

- 需要重新设计 DSH 和 Python 之间的通信。
- 需要重写原有消息接入和会话逻辑。
- 需要重新适配现有 Web 面板。
- 需要维护两套运行体系，甚至最终变成三套。

> 这对一个人开发项目来说，初期成本比较高。

> 但我也不建议所有东西都用 Node.js。例如，后续你想让蓝余汐：

- 阅读 PDF、Word、Excel。
- 自动学习 B 站视频。
- 识别图片和视频。
- 使用本地 Embedding 模型。
- 做知识提取和实验验证。

### 二、数据库选型：从 MySQL 换成 PostgreSQL

> 这里我想稍微调整一下上一条方案：如果蓝余汐是一个普通的社交机器人，MySQL 完全够用；但你想做的是长期记忆、知识关联、自主学习、人格演化的 Agent 系统。这种情况下，我更推荐 PostgreSQL。
> 原因不是 MySQL 不好，而是蓝余汐未来的数据类型比较复杂。

| 需求 | MySQL | PostgreSQL |
|---|---|---|
| 普通业务数据 | 很好 | 很好 |
| 人物关系、记忆关系 | 很好 | 很好 |
| JSON 结构化数据 | 支持 | JSONB 更灵活 |
| 全文检索 | 支持 | 支持，能力较丰富 |
| 向量检索 | 需要额外方案或依赖具体版本能力 | pgvector 扩展成熟 |
| 复杂数据查询 | 很好 | 很好 |
| AI 知识库整合 | 通常需要搭配外部向量库 | 可以先在一个数据库内完成 |

> **为什么向量检索很重要？** 假设蓝余汐以前学过 Unity 动画，但记忆里没有出现主人提问时使用的原词。主人问：「之前我们研究过角色移动时切换动画的问题吗？」

> 向量检索可以根据语义找到这些内容。PostgreSQL 配合 pgvector，可以先把普通记忆和向量数据放在同一个数据库里，减少初期维护成本。

**我的数据库选择（卡片）**

| 组件 | 定位 | 内容 |
|---|---|---|
| PostgreSQL | 推荐主数据库 | 身份、人格、事件、记忆、人物关系、学习目标、技能、权限、审计 |
| pgvector | 向量扩展 | 记忆向量、知识向量、语义相似度检索 |
| Redis | 后续引入 | 等到任务并发和调度需求增加时再引入 |
| 文件存储 | — | 保存图片、音频、视频、PDF、原始资料；数据库只保存文件元信息和存储路径 |

> 我不建议第一天就同时部署 MySQL、PostgreSQL、Redis、Qdrant、Elasticsearch。对个人项目而言，这会增加很多没有必要的维护成本。
> 如果你更希望沿用熟悉的 MySQL，也完全可以采用 MySQL + Qdrant 的方案。但从蓝余汐的长期 AI 数据需求看，我会优先选 PostgreSQL + pgvector。

### 三、后端架构（节标题原文未抄到）

    蓝余汐 Core Backend  ·  Node.js + TypeScript  ·  唯一的业务核心与 Agent 控制中心
      ├─ Agent Engine     认知、规划、决策、执行
      ├─ Memory Engine    记忆、人物、关系、检索
      ├─ Learning Engine  目标、任务、学习流程
      ├─ Growth Engine    反思、人格、成长档案
      ↓
    统一服务接口（REST API · 内部 RPC · Event Bus）
      ↓
    AI Worker（Python + FastAPI）文档解析 / 视频处理 / 图片理解 / Embedding / AI 实验 / 专项推理
      ↓
    PostgreSQL + pgvector（长期数据、记忆、向量、任务记录）

**3.1 Node.js 核心后端负责什么**

| 项 | 选型 |
|---|---|
| 运行环境 | Node.js |
| Web 框架 | Fastify |
| 参数验证 | Zod |
| 数据访问 | Drizzle ORM |
| 数据库 | PostgreSQL |
| 定时任务 | 持久化任务调度器 |
| 实时通信 | WebSocket |
| 日志 | Pino |

> 为什么选择 Fastify？轻量，适合个人项目；性能好，插件化程度高；TypeScript 支持不错；可以与现有 DSH 插件比较自然地整合。
> 如果你希望更强的企业级模块管理，也可以选 NestJS。但我的第一选择是 Fastify，因为蓝余汐的重点是 Agent 业务逻辑，不需要一开始就引入很重的框架体系。

**3.2 Python 后端负责什么**

> Python 不应该再实现一遍完整的蓝余汐业务系统。它应该是一个专门提供 AI 能力的 Worker 服务。

| 库 / 框架 | 用途 |
|---|---|
| FastAPI | 提供内部 HTTP 接口 |
| Pydantic | 数据结构验证 |
| PyTorch | 模型推理和实验 |
| sentence-transformers | Embedding |
| Transformers | 模型加载与推理 |
| PyMuPDF | PDF 解析 |
| python-docx | Word 解析 |
| OpenCV / FFmpeg | 视频、图像处理 |

> 例如，Node.js 收到一个 B 站视频学习任务：

1. Node.js 检查该视频是否属于授权资源。
2. Node.js 创建学习任务。
3. Python Worker 获取视频或字幕处理任务。
4. Python 提取字幕、章节、关键内容。
5. Python 返回结构化学习材料。
6. Node.js 调用认知引擎分析。
7. Node.js 将学习结果写入 PostgreSQL。
8. Learning Engine 决定是否需要继续实验和验证。

> 这样两个服务不会互相抢业务职责。

### 六、权限与安全：高自主性必须有明确的边界

> 这部分我建议作为 **P0 基础设施**，不能等功能做完再补。我建议实现一个统一的 PolicyEngine。每次数据读取、记忆写入、模型调用、工具执行，都经过权限判断。

    interface PolicyEngine {
      canRead(subject: string, resource: string, purpose: string): Promise<boolean>;
      canRemember(sourceId: string, …): Promise<boolean>;
      canExecute(action: string, target: string): Promise<AuthorizationResult>;
    }

> 尤其要注意四件事：

1. 未授权的 QQ 群不能进入学习系统。
2. 私聊记忆不能因为统一记忆而自动暴露到群聊。
3. 不能将聊天记录默认用于 LoRA 训练。
4. 模型输出的指令不能绕过权限检查直接执行工具。

> 另外，QQ、微信和 B 站的接入要遵守平台规则、授权范围及第三方隐私要求。特别是群聊中的其他成员，不应该被默认为同意长期保存其内容。

| M4 高自主 Agent | 预计 3~4 周 | P2 | （条目未抄到） | 系统重启后可以恢复未完成学习任务，且任务不会无限循环 |
| M5 多平台和多模态 | 持续迭代 | P2 | 微信正式接入；图片和视频理解；语音交互；Live2D 表达；模型微调实验；更丰富的成长展示 | 多个平台共享同一人格和记忆体系，权限与上下文依然隔离 |

> 我建议 **M0、M1、M2 是真正的第一阶段目标**。没有可靠记忆，学习无法积累；没有学习验证，成长就容易被模型自说自话；没有权限系统，高自主性反而会带来风险。

### 九、Web 管理面板应该增加什么？

> 现有 Web 面板不应该只是查看日志、修改配置和启停机器人。我希望未来它可以成为蓝余汐的成长管理中心。

| 新页面 | 看什么 |
|---|---|
| 人格档案 | 身份、性格、兴趣、人格变化历史 |
| 记忆世界 | 经历、人物、知识、关系和来源 |
| 学习中心 | 学习目标、任务进度、技能评估 |
| 成长时间线 | 每日反思、成长事件、认知变化 |

> 还应该有三个管理页面：

- **数据授权中心**：查看 QQ 群、联系人、B 站资源的授权范围，支持撤回。
- **自主行动中心**：查看她正在做什么、为什么做、消耗多少资源，可以暂停。
- **模型与预算中心**：查看云端与本地模型使用量、调用成本、失败情况。

> 这样你不仅可以和蓝余汐聊天，还可以观察她如何学习、为什么产生某个目标、依据什么形成某个认知。

### 十一、我对这套架构的最终建议

> 有三件事我希望你从第一天就坚持：

> **第一，记忆是蓝余汐的长期资产。** 不能依赖某个模型的上下文窗口，也不能把所有历史聊天塞进 Prompt。记忆必须可以独立保存、检索、更新和迁移。

> **第二，成长必须有证据。** 蓝余汐可以认为自己喜欢某个话题，但系统应该区分一次兴趣表达、持续行为倾向和已经稳定的人格特征。她可以提出自我认知，但不能把模型生成的结论直接当成客观事实。

> **第三，自主性必须能够被观察和管理。** 主人应该能够看到她为什么创建学习目标、正在使用什么资料、调用了哪个模型、完成了什么行动，以及哪些内容需要自己批准。

> 这套系统可以逐渐形成很强的数字个体连续性，但我们仍然应该把它准确地称为持续成长的数字智能体，而不是已经证明具有人的主观意识。

### 收尾

> 我不建议你把蓝余汐做成 Node.js 机器人 + Python AI 服务 + Java 业务后端 三个平级系统。你虽然有 Java 开发经验，但这里没有必要再引入第三种后端语言。
> 保持一个核心、一个 AI 扩展服务、一套数据库，会更容易长期维护。
> 下一步最值得做的是把数据库结构和后端项目骨架真正搭出来，而不是先写复杂的 Agent。我可以继续帮你制定一套可以直接初始化仓库的目录、依赖清单、Docker Compose、数据库迁移 SQL 和接口代码。
